# 결함 고치기 — `tools/numbers.py`의 이슈 40, 41

**상태: 준비됨(2026-11-19). 소유자가 고친다.** 고칠 파일은 1단계에서 본인이 쓴 `src/tabletrace/tools/numbers.py`다. AI 도구는 이 명세, 테스트(`tests/test_numbers_fix.py`), 데이터를 다시 만들고 영향을 세는 스크립트(`scripts/numbers_fix.py`)만 만들었다. 코드는 쓰지 않는다.

## 왜 하는가

1단계 다시 쓰기에서 원래 코드의 결함 두 개를 찾았다(`docs/dev/issues-log.md`의 40, 41). 그때는 "고치면 학습 데이터가 바뀐다"는 이유로 고치지 않고 기록만 했다. 지금까지는 "찾았다"까지만 말할 수 있었다. 고치고 영향을 재면 "찾아서 고쳤고, 무엇이 바뀌는지 쟀다"가 된다.

## 미리 잰 영향

AI 도구가 실험용 사본에 임시로 고쳐 넣고 쟀다(그 사본은 저장소에 없다). 고치는 방법이 아래 A든 B든 지금 데이터에서는 결과가 같다.

| 무엇 | 바뀌는 것 |
|---|---|
| 표에 저장된 머리글 단위 | 7개 표(한국어 4, 화학 교과서 3). 단위가 아닌 말이 빠진다 |
| 합성 문항 | 화학 **학습** 문항 10개의 정답(이슈에 적힌 4 + 6개). 한국어 합성 문항, 화학 개발 문항, 평가 문항은 바뀌지 않는다 |
| 저장된 모델 출력의 검증 판정 | 39,504건(저장된 출력 × 검증 설정 3개, 정답 프로그램, 화학 논문 문항 포함)에서 **차이 0** |
| 전체 테스트, 데이터 검사, 수치 검사 | 모두 통과(436개 통과, 수치 4,535개 일치) |

즉 보고한 숫자는 하나도 바뀌지 않는다. 바뀌는 것은 화학 모델 학습에 쓴 문항 10개의 정답이다. 그 정답으로 학습한 모델을 다시 학습할지는 따로 정한다(GPU 필요, 선택).

## 결함 40: `format_number`가 아주 작은 값을 `0`으로 쓴다

지금은 "정수에 가까운가"를 먼저 본다. `abs(x - round(x)) < 1e-9`이면 정수로 쓰는데, 0이 아니면서 절댓값이 `1e-9`보다 작은 값도 여기 걸려 `0`이 된다. 화학 학습 문항에서 전자의 전하(1.602e-19 C)가 `0`, 양성자의 질량(1.672e-24 g)이 `0 g`로 적혔다.

고친 뒤 지킬 것:

- 0이 아니고 절댓값이 `1e-3`보다 작은 값은 항상 `f"{x:.3e}"`로 쓴다. 예: `1.602e-19` → `"1.602e-19"`, `2.31e-27` → `"2.310e-27"`, `-5e-12` → `"-5.000e-12"`.
- `0`, `0.0`, `-0.0`은 `"0"`.
- **그 밖의 값은 지금과 한 글자도 다르면 안 된다.** 바뀌는 범위는 `0 < |x| < 1e-9`뿐이다. `2.0000000001`은 여전히 `"2"`, `0.001`은 `"0.001"`, `123456.7`은 `"1.235e+05"`다.

생각해 볼 점: 계산 중에 생기는 아주 작은 오차(`0.1 + 0.2 - 0.3`은 `5.55e-17`)도 이제 `"5.551e-17"`로 나온다. 지금 데이터에는 이런 결과가 없다(위 영향 측정). 정밀한 값과 계산 오차를 숫자만 보고는 가를 수 없다는 것이 이 함수의 한계다.

## 결함 41: `header_unit`이 괄호 안의 단위 아닌 말을 단위로 받는다

지금 규칙은 괄호 안이 단위 목록(`UNIT_TOKENS`)에 있거나, "영문자·숫자·몇몇 기호로 된 1~10글자"면 단위로 본다. 뒤의 느슨한 규칙 때문에 세 코퍼스의 머리글 말 31개가 단위가 되는데, 그중 12개는 단위가 아니다. 그 결과 화학 학습 정답에 `"0.9 measured"`, `"3 predicted"`처럼 말이 붙었다.

느슨한 규칙으로만 단위가 되는 31개(세 코퍼스 전부):

| 단위가 아니다 (12) | 단위다 (19) |
|---|---|
| `UTC`(발생일시), `MVP`(최우수선수상), `NTV`·`YTV`·`STV`(방송국), `max`(높이), `t1/t2`(층수) | `ft`, `MT`(톤), `kW` |
| `state`, `predicted`, `measured`, `Kw`(물의 이온곱, 깨진 머리글 `pKwpKw = –log10(Kw)`) | `M`, `amu`, `mN/m`, `J/K·mol`, `J/g °C`, `L/mol`, `mPa·s`, `mPa s`, `mol/L/s`, `L/mol/s`, `V`, `Pa` |
| `T`(계산 방법 이름 `CCSD(T)`. 이 표는 단위를 손으로 꺼 두었다) | `kJ mol^-1`, `Jm^5`, `kcal / mol`, `g / mol` |

### 본인이 정할 것: 어디서 선을 긋는가

| 방법 | 내용 | 처음 보는 머리글에서 |
|---|---|---|
| A. 닫힌 목록 | 목록에 있는 것만 단위로 본다. 위의 진짜 단위 19개를 목록에 더한다 | 처음 보는 단위는 놓친다(단위 없음) |
| B. 느슨한 규칙 + 제외 목록 | 지금 규칙을 두고, 단위가 아닌 12개를 뺀다 | 처음 보는 단위 아닌 말은 여전히 단위가 된다 |

판단 재료: 단위가 아닌 말이 단위가 되면 그 말이 정답에 붙어 나가고 단위 검사가 엉뚱한 것을 비교한다. 단위를 놓치면 단위 검사 하나를 건너뛸 뿐이다. AI 도구는 A를 권한다. **정하는 것은 본인이다.** 테스트는 둘 다 통과한다(미리 확인했다).

주의할 것 하나: 진짜 단위 19개를 `UNIT_TOKENS`에 넣으면 안 된다. `UNIT_TOKENS`는 `parse_number`가 **셀 값**의 끝에서 단위를 떼어 낼 때도 쓴다. 1단계에서 "셀 값에서는 `M`을 단위로 보지 않는다"고 정했고, 저장된 셀 34,561개가 그 규칙으로 읽혔다. 머리글에서만 쓰는 목록을 따로 두면 된다. 테스트 `test_reading_cells_is_unchanged`가 이것을 본다.

### 테스트가 요구하는 것

- 위 12개는 `None`, 19개는 그 단위.
- 기존 동작은 그대로: `"매출액 (억원)"` → `"억원"`, `"값 (단위: 명)"` → `"명"`, `"관객수 （명）"`(전각 괄호) → `"명"`, `"Temperature, °C"`(쉼표 형식) → `"°C"`, `"Radial nodes (no.)"`·`"Year (2015)"`·`"Rate, measured"` → `None`.

`impact`가 위 "미리 잰 영향"과 같게 나오면 된다: 셀·머리글·표기 35,803개 가운데 머리글 12개와 작은 값 16개의 표기만 다르고(셀 읽기 차이 0), 표 7개의 단위, 화학 학습 문항 10개, 판정 차이 0. 다르게 나오면 푸시하기 전에 알려 주면 같이 본다.

데이터 파일 세 개는 스크립트가 만든 것이다. 본인이 쓴 것이 아니라 본인 코드의 결과물이므로 같은 커밋에 넣는다. 넣지 않으면 CI의 데이터 검사(`check_data.py`)가 실패한다. 합성 문항의 정답이 계산기의 새 결과와 달라지기 때문이다.

푸시했다고 알려 주면 AI 도구가 브랜치를 받아 테스트와 `impact`를 다시 돌려 리뷰한다. 통과하면 GitHub에서 Pull request를 만들어 `main`에 합친다. 합친 뒤 AI 도구가 이슈 기록(40, 41을 "수정")과 `LOG.md`, 전달 문서를 고친다.

## 면접에서 물을 만한 것

- 왜 처음에 고치지 않았나: 고치면 학습 데이터가 바뀌어 저장된 결과와 맞지 않을 수 있었다. 그래서 영향을 먼저 재고 고쳤다. 잰 결과 보고한 숫자는 바뀌지 않았다.
- 닫힌 목록과 느슨한 규칙 가운데 무엇을 골랐고 왜인가. 어느 쪽 실수가 검증기에 더 해로운가.
- `format_number`가 계산 오차와 진짜 작은 값을 가를 수 없는 이유.
